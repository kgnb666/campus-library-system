# 文档公开范围评估清单 (Stage 10-J 任务 6)

> **本文件是一份"待决策清单"，不是删除指令。** 仓库内没有删除任何文档。
> 下面把 `docs/` 下的 44 个文件按性质分成两类，并给出三档处置建议，由项目所有者决定。

## 一、为什么要做这件事

`docs/Stage8-Final-Risk-Report.md` 记载的答辩应对口径中，有一条是
"**完整版本演进历史 + 每次严格 Design Review 的过程文档**"，
同时声明相关架构"**网络上绝无雷同模板**"。

而 `docs/` 下的另一批文件（如 `REPAIR-PROMPTS.md`、`FINAL-Deep-Audit.md`、
`FIX-PROMPTS-BY-STAGE.md`）逐条记录了**缺陷自曝、整改提示词与修复过程**，
其中包含大量"本项目曾存在什么问题、如何被逐条发现并修掉"的内容。

两者并不矛盾 —— 一份诚实的工程记录本来就该同时包含"设计"和"发现设计里的错"。
但如果这些过程材料的**受众与定位没有明确**，就会出现两种风险：

1. 对外展示时被误读为"项目初期质量很差"（实际上它记录的是**已修复**的问题）；
2. 与"绝无雷同"的表述放在一起时，读者会追问"这些逐条整改的提示词是谁写的"。

因此需要**明确每一份文件的受众**，而不是简单地删或留。

## 三、三档处置建议

### 第 1 档：公开发布（随仓库一起对外）
- A 类全部；
- C 类**可选**公开发布 —— 如果对外想强调的是"工程严谨性"，这批材料恰恰是最有力的证据：
  它们记录了问题如何被发现、如何被验证修复，以及每条修复的验收标准。
  前提是**在文件开头明确说明材料的性质与生成方式**（见下方"关于披露的提醒"）。

### 第 2 档：仅本地保留（不进公开仓库，但保留在工作副本）
- B 类中偏内部管理性质的文件：阶段完成报告、Design Review、审计报告；
- 建议做法：把 `docs/` 拆分为 `docs/design/`（A 类）与 `docs/process/`（B+C 类），
  公开仓库只推送 `docs/design/`，`docs/process/` 保留在本地。
  **目录拆分比 `.gitignore` 更可控**：后者对已跟踪文件无效，必须先 `git rm --cached`，
  一旦有人克隆历史仍可能看到旧版本。

### 第 3 档：移出仓库（`.gitignore` + `git rm --cached`）
- 仅当材料包含**真实凭据、生产地址、个人隐私或商业敏感信息**时才应使用这一档；
- 当前 `docs/` 下**没有发现**上述内容（密钥已于阶段十-A 全部移出源码与历史索引），
  所以这一档目前**建议不使用**。

## 四、关于披露的提醒（重要）

`.gitignore` 能让文件不被提交，但它**无法改变已经发生的事实**，也不适合用来规避
学术规范中关于"工具使用与协作方式披露"的要求。如果所在学校/期刊要求说明
开发过程中使用了哪些辅助工具，**应以学校/期刊的要求为准如实披露**，
而不是通过仓库可见性来规避。这一条属于项目所有者与其学术机构之间的合规问题，
需要由所有者自行判断，本文只提供工程层面的分类建议。

## 五、需要所有者决策的三个问题

1. C 类整改过程材料是否随仓库公开？（建议：公开，但补一句材料性质说明）
2. 是否采用 `docs/design/` + `docs/process/` 的目录拆分？
3. 是否存在我未识别出的敏感内容（如真实单位名称、内部接口地址）需要移出？
