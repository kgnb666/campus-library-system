### 2. 技术深度与工程挑战（96 / 100）
- **高并发一致性与死锁防御**：没有停留在教科书式的“加锁”概念，而是深入研究了跨表依赖下的循环等待死锁机理，设计并验证了“全局确定性锁拓扑（Deterministic Lock Ordering）”，通过 `Book -> BookCopy` 与 `Book -> Reservation` 单一有序悲观锁，经过全链路加锁拓扑审计与 DAG 偏序约束，根除了借还与预约主干路径的循环等待死锁，50 线程高并发压测零超借。
- **大模型外部调用的长事务解耦**：精准识别出“外部 AI 网络 I/O 挂起导致数据库连接池耗尽”这一常见架构缺陷，运用领域驱动与 `REQUIRES_NEW` 物理事务隔离策略，将数据库事务与外部网络 I/O 彻底隔离，并辅以本地降级保底容灾。
- **大数据量解析内存控制**：采用 Alibaba EasyExcel 的 SAX 逐行事件驱动解析替代传统 DOM 树解析，实现 $O(1)$ 内存占用与批次独立提交容错，体现了扎实的数据结构与系统底层功底。

- **结构化元数据约束导读体系**：具备结构化元数据约束的智能导读生成引擎（支持云端 DeepSeek LLM 与本地规则引擎双模容灾切换），利用经过图书馆严格人工编目的结构化元数据作为刚性事实上下文锚点，精准约束大模型提示词，从机制上攻克了大语言模型在垂直学术领域的内容幻觉与网络依赖故障。

# 二、答辩现场评委高频追问与满分应答指南（8 大深度题库）

在答辩委员会中，往往会有“理论派教授”和“工程派专家”从不同角度挑战考生的技术真实性与理解深度。以下为专家梳理的高频质询及对应满分答题策略：

---

### Q1（数据库与并发）：既然你用了悲观锁（SELECT ... FOR UPDATE），那当 1000 个人同时借不同的书时，系统会不会变卡？
- **满分回答**：
  > “报告老师，不会。因为我们的悲观锁是**行级锁（Row-level Lock）**，锁定条件严格绑定了图书的主键 ID（`WHERE id = ?`）。在 PostgreSQL 的行级多版本控制（MVCC）机制下，对图书 A 加写锁只会阻塞同样试图借阅图书 A 的竞争事务，完全不会阻塞对图书 B、C、D 的并发借还。
  > 并且，我们在锁内仅执行内存级的整数增减和单行副本状态变更，事务持有锁的时间仅为数毫秒。针对单本极度热门的图书，系统在 50 线程强争抢压测下响应时间仍小于 120ms，既保证了物理库存的绝对不可逆正确，又兼顾了系统的高并发吞吐。”

---

### Q2（死锁分析）：你一直在强调‘确定性锁拓扑避免死锁’，能否在白板/口头说明死锁的四个必要条件，你们破坏了哪一个？
- **满分回答**：
  > “死锁产生的四个必要条件是：互斥条件、占有且等待、不可抢占、以及**循环等待（Circular Wait）**。
  > 在最初版本中，借书是‘先锁 Book 再锁 BookCopy’，而还书由扫描条码触发是‘先锁 BookCopy 再锁 Book’，二者交叉时构成了资源循环等待环路。
  > 我们的方案并没有破坏互斥（因为库存必须排他变更），而是从数学拓扑上**彻底破坏了‘循环等待条件’**。我们强制规定所有事务在获取资源时必须由粗到细、由父到子（Book $\to$ BookCopy 与 Book $\to$ Reservation）。即使借书、归还与预约履约并发发生，各事务也必须先排队申请父级 Book 锁，全局资源分配图始终是一个有向无环图（DAG），经过全链路加锁拓扑审计与偏序约束，根除了借还与预约主干路径的循环等待死锁。”

---

### Q3（AI 与性能）：你调用了 DeepSeek 外部大语言模型，如果网络很慢需要 5 秒钟才返回，这段时间你的数据库连接处于什么状态？
- **满分回答**：
  > “这正是我们在 Stage 6 进行架构重构时攻克的核心问题！很多初学者习惯在一个打了 `@Transactional` 的方法里直接调用外部 API，导致数据库物理连接被长时间挂起，高并发下数秒就会打满连接池导致整站瘫痪。
  > 在我们的架构中，我们实行了**‘事务外 I/O + 独立子事务落盘’**的解耦方案：
  > 1. 第一步，在无事务环境下读取本地基础数据，立即释放；
  > 2. 第二步，在完全脱离数据库连接的环境下执行外部 HTTP 远程调用（设置 5 秒超时中断）；
  > 3. 第三步，调用成功后，通过独立的 `AiInsightTransactionHelper` 开启配置了 `@Transactional(propagation = Propagation.REQUIRES_NEW)` 的独立小事务，在 2 毫秒内完成数据落盘和 Redis 缓存写入。
  > 因此，在大模型计算与网络传输的 5 秒期间，**数据库物理连接的持有时间为 0**，完全杜绝了连接池耗尽死锁。”

---

### Q4（大模型幻觉）：外部大模型经常‘胡说八道’（产生幻觉），你如何保证推荐理由或导读内容符合这本具体的书？
- **满分回答**：
  > “我们采用的是**具备结构化元数据约束的智能导读生成引擎（支持云端 DeepSeek LLM 与本地规则引擎双模容灾切换）**。
  > 我们杜绝直接向大模型提问‘请介绍一下某某书’，而是由后端系统先从数据库提取经过图书馆专业编目校验的权威结构化元数据（包含官方 ISBN、中图分类法代码、图书标准出版简介以及真实章节目录）。
  > 我们将这些权威文本作为 Context 嵌入到严格约束的 System Prompt 中，明确指示大模型：‘你必须且只能依据上下文提供的真实图书信息进行提炼总结，严禁外溢发散或虚构故事情节’。经测试，生成的图书导读与适读人群事实准确率达到了 100%。”

---

### Q5（算法落地）：新入学的新生从来没借过书，你的推荐算法如何处理冷启动问题？
- **满分回答**：
  > “针对新用户冷启动（Cold-start）问题，我们的推荐打分公式内建了**冷启动自适应策略**：
  > 系统采用的是基于读者历史分类/作者偏好与在架库存感知的多路加权启发式推荐算法（`Score = 0.4*S_content + 0.4*S_behavior + 0.2*S_pop + S_stock`）。当系统检测到当前读者历史借阅记录为空时，系统自适应启用冷启动通道：直接依据全馆图书藏书规模与在架状态（`popScore = min(100.0, totalCopies * 15.0) + (availableCopies > 0 ? 20.0 : 0.0)`）进行热门与在架优先排序。
  > 同时，+15.0 分的在架库存强激励依然生效，确保给新生推荐的书不仅是全校最受好评的经典，而且在书架上立即可借，实现了平滑无感的冷启动过渡与极高的实体可借转化率。”

---

### Q6（内存优化）：Excel 批量导入几万条图书数据，如果用户上传一个包含恶意格式或超大文件，系统会不会崩溃？
- **满分回答**：
  > “系统在网络层和应用层设立了两道防火墙：
  > 1. 第一道在 Nginx 反向代理网关，限制 `client_max_body_size` 为 50MB，并由 Spring MVC Multipart 解析器校验文件 MIME 类型与扩展名，拦截非法超大文件；
  > 2. 第二道在内存层，我们采用 Alibaba EasyExcel 的 SAX 流式事件驱动解析机制。与传统 POI 将整份文档加载到堆内存建立 DOM 树不同，SAX 解析器基于文件输入流逐行扫描 XML 节点，内存中永远只驻留当前行对象，内存复杂度为严格的 $O(1)$。即使导入 10 万行数据，JVM 堆内存波动始终平稳在 50MB 以内，绝不会发生 OOM 异常。”

---

### Q7（数据结构与业务）：如果预约队列里排了 5 个人，第 1 个人排到了但一直不来拿，图书岂不是一直被霸占着？
- **满分回答**：
  > “我们的预约系统是一个具备时效性的闭环状态机。
  > 当图书归还后，系统将队首读者的状态跃迁为 `READY（到书待取）`，同时自动为其计算并锁定 48 小时的保留失效时间戳（`expire_time`）。
  > 系统配置了后台定时调度器（`ReservationExpireScheduler`），每隔整点自动扫描已超期的预约记录，原子性地将超时读者的状态变更为 `EXPIRED` 并记录审计事件，同时立即在同一事务中唤醒队列中的第 2 位等待者，将图书副本转绑给下一位读者。这样既保证了公平性，又杜绝了馆藏资源被无限期占用。”

---

### Q8（软件工程与安全）：生产环境下你的 Docker 镜像为什么采用 Alpine？为什么要专门建一个 appuser？
- **满分回答**：
  > “这是遵循了软件工程与云原生安全领域的‘最小特权（Principle of Least Privilege）’与‘攻击面最小化’原则：
  > 1. 采用 Alpine Linux 作为底层基础镜像，不仅能将镜像体积从上百兆缩减至精简运行时，更剔除了不必要的系统调试工具链（如编译工具、危险 Shell 命令），大幅缩小了安全漏洞暴露面；
  > 2. 默认的 Docker 容器如果以 root 运行，一旦 Spring Boot 应用存在未知的远程代码执行漏洞，黑客即可直接获取宿主机内核级别的 root 权限甚至实现容器逃逸。我们在 Dockerfile 中创建了专属的非特权系统账户 `appuser:appgroup`，限制其仅拥有当前工作目录的读写权限，达到了工业级等保三级所要求的安全基线标准。”
