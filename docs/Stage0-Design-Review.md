## 3. 核心业务规则与领域决策

### 3.1 图书（Book）与物理副本（BookCopy）拆分
* **[Decision]**：必须严格拆分为 `books`（书目）与 `book_copies`（物理副本）两张表，呈 1 对 N 关系。
* **[Reason]**：ISBN 对应的是书目的抽象出版物版本，而借出、归还、损毁、索书号对应的是单本具体的实物。若合并会导致库存变成数字，无法追踪具体哪一本书在架、哪一本书被谁借走以及损毁定责。
* **[Impact]**：借阅单外键强绑定 `copy_id`，彻底具备物理流转可追溯性。

### 3.2 副本状态多值化（拒绝布尔值）
* **[Decision]**：状态采用 7 态枚举：`AVAILABLE`, `BORROWED`, `RESERVED`, `MAINTENANCE`, `DAMAGED`, `LOST`, `SCRAPPED`。
* **[Reason]**：真实图书馆中，一本书不在书架上并不一定等于被读者借走，可能是被预约锁定、送去装订修补、或损坏待赔偿。

### 3.3 借阅规则动态化与防逾期续借
* **[Decision]**：建立 `borrowing_rules` 规则表，支持针对学生、研究生、教师配置最大借阅数、天数、续借次数。
* **[Rule Hard Boundary]**：**严禁逾期后续借（`allow_overdue_renew = false`）**，只要读者名下有 1 本书逾期未还，其所有借阅与预约资格即刻冻结。

### 3.4 预约机制防刷设计
* **[Decision]**：仅在目标书目 `available_copies == 0` 时开放预约入口；单读者对单书目最多存在 1 条活跃预约单；预约到馆为读者保留 48 小时，超时通过定时调度任务自动移交下一位候补人或释放回在架。

## 4. 并发控制方案（最后一本书防超借）

* **核心痛点**：2 名或多名学生在同一毫秒争抢借阅最后一本在架图书。
* **三层防御方案**：
  1. **第 1 层（业务行锁）**：在事务中执行 `SELECT * FROM book_copies WHERE barcode = :barcode FOR UPDATE`，锁住目标物理副本行，排队串行化执行。
  2. **第 2 层（原子扣减校验）**：`UPDATE books SET available_copies = available_copies - 1 WHERE id = :bookId AND available_copies > 0;`。若受影响行数为 0，立即触发事务回滚并抛出 `COPY_NOT_AVAILABLE`。
  3. **第 3 层（数据库级 Check 约束保底）**：`CHECK (available_copies >= 0)`。从物理引擎层根除库存出现负数的可能性。

---

## 5. 权限与安全方案（RBAC + 防 IDOR）

1. **RBAC 权限模型**：预置 `ROLE_STUDENT`、`ROLE_LIBRARIAN`、`ROLE_ADMIN`，接口全量受 Spring Security 注解保护。
2. **防水平越权（IDOR）**：
   * 读者查询个人借阅单 `GET /borrow-records/{id}` 时，业务层硬性校验 `record.getUserId().equals(currentUser.getId())`，防止恶意枚举 ID 刺探他人借阅隐私。
3. **凭证生命周期**：
   * AccessToken（JWT，有效期 2 小时）+ RefreshToken（Redis 托管，有效期 7 天）。注销时将 AccessToken JTI 写入 Redis 黑名单，即刻吊销。

## 6. AI 模块架构（DeepSeek Grounded-RAG）

* **[Decision]**：AI 荐书必须走“**用户问答 → 提取关键词 → PostgreSQL 检索在架真实图书 → 注入 Context → DeepSeek 智能排序与写推荐词 → 返回真实书目卡片**”的流程。
* **[Reason]**：绝对杜绝 AI 凭空编造不存在的书名。
* **[Fallback]**：若 DeepSeek 调用超过 5 秒或接口报错，自动降级为传统馆藏数据库匹配展示，保证用户界面不白屏、不报错。

## 8. 风险清单与应对策略

1. **并发竞态风险**：高并发压测时容易因锁范围过大造成数据库死锁。
   * *应对策略*：保证事务中锁资源顺序固定（先锁 `book_copies`，再更新 `books`），避免循环等待；使用 `SKIP LOCKED` 避免线程大量饥饿阻塞。
2. **AI 超时抖动风险**：公网大模型 API 容易受网络延迟影响导致接口卡顿。
   * *应对策略*：设置 5 秒硬超时限制，配置 CircuitBreaker 熔断降级。
3. **物理条码重复风险**：手动输入条码容易重码。
   * *应对策略*：条码统一由后端按日期流水算法自动生成，并在数据库 `barcode` 列设置唯一索引（UNIQUE）。
