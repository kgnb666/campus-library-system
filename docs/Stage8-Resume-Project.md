**核心技术栈**：Java 21、Spring Boot 3.3、Spring Security、JPA/Hibernate、PostgreSQL 17、Redis 8、Flutter 3、Docker Compose、EasyExcel、DeepSeek API  

**项目描述**：  
针对高校图书馆在选课季与考试周遭遇的热门图书高并发秒杀借还、跨表循环死锁、新进图书推荐冷启动及大模型外部调用拖垮数据库连接池等核心痛点，主导研发的集“细粒度库存流通、FIFO 预约排队、多路加权启发式推荐与受控元数据约束智能导读”于一体的企业级数字图书馆系统。

**核心贡献**：
1. **高并发库存一致性控制与死锁防御**：深入剖析借还与预约流程交叉调用时的循环等待死锁隐患，推导确立**全局确定性锁拓扑与 DAG 偏序模型（Deterministic Lock Ordering）**，统一固化从父实体到子实体的行级排他锁获取顺序（`SELECT ... FOR UPDATE`），经过全链路加锁拓扑审计与偏序约束，根除了借还与预约主干路径的循环等待死锁，50 线程强争抢压测下超借率为 0；
2. **大模型调用长事务物理解耦与保底容灾**：针对外部 DeepSeek LLM 接口 2~4 秒网络 I/O 长期占用数据库连接池的隐患，采用“事务外 HTTP 纯网络调用 + `REQUIRES_NEW` 独立子事务秒级落盘 + Redis 缓存”的架构重构，彻底杜绝连接池枯竭，并引入本地规则引擎实现 100% 熔断降级容灾；
3. **闭环 FIFO 预约状态机流转设计**：基于数据库排他锁与自增序列保障排队号原子单调递增，结合 Spring 领域事件机制在图书还书事务提交后毫秒级唤醒队首读者并锁定物理副本，配合整点定时调度器实现 48 小时逾期未取自动清退与顺延；
4. **基于读者偏好与在架感知的多路加权启发式推荐**：构建结合读者历史分类/作者偏好（40%）、阅读轨迹行为偏好（40%）、全馆借阅热度（20%）并叠加实时在架库存强激励（在架可借时 +15.0 分）的多路加权启发式推荐模型（`Score = 0.4*S_content + 0.4*S_behavior + 0.2*S_pop + S_stock`），结合 PostgreSQL 复合索引将高潜候选集初筛下推至存储层，推荐计算耗时由 820ms 降至 45ms 以内，兼顾冷启动与物理库存可借转化率；
5. **大规模 Excel 流式编目导入优化**：使用基于 SAX 事件驱动的 EasyExcel 替换传统 POI DOM 解析，实现 $O(1)$ 常数级堆内存占用，设计“每 100 条分批独立事务提交 + 行级格式校验容错”，成功抵御数万行导入下的 OOM 崩溃；
6. **生产级容器化微服务编排与自动化冷备交付体系**：构建后端 Alpine JRE 21 多阶段镜像（体积缩减 75% 至 215MB），践行最小特权非 root 用户运行，Redis 用于会话刷新凭据托管与防刷频控，核心库存依托 PostgreSQL 行级锁保障强一致性，集成 Nginx 网关与全自动数据库冷备恢复脚本（`backup.sh` / `restore.sh`），全套服务支持 Docker Compose 一键编排拉起。

## 针对大厂面试官的高频连环追问应对指南

### 深度追问 1：既然用了行级悲观锁，为什么不选择 Redis 分布式锁或者乐观锁？
- **面试官意图**：考察候选人在“悲观锁 vs 乐观锁 vs 分布式锁”选型时的技术权衡深度，以及对业务场景的敏感度。
- **满分回答**：
  > “我们在架构设计阶段深入对比了这三种方案：
  > 1. **为什么不用乐观锁（CAS + Version）？**  
  > 在期末考试或选课季，全校可能几十上百人瞬间争抢某一本必考教材（如《计算机网络》孤本）。如果使用乐观锁，由于只有一个线程能成功，其余线程将频繁发生版本冲突导致大量重试，这不仅白白浪费 CPU 算力，更会导致数据库连接数飙升，重试失败率过高严重伤害用户体验；
  > 2. **为什么核心库存不用 Redis 分布式锁？**  
  > 图书借阅不仅涉及库存数字的增减，还紧密依赖关系型数据库中物理副本状态变更、借阅历史台账生成、用户最大借阅量限制等多表外键关联约束。如果在 Redis 扣减而在数据库落盘，一旦应用崩溃或网络分区，极易出现 Redis 与 DB 双写不一致；
  > 3. **悲观行级锁的优势**：  
  > 我们的行级排他锁直接精确到主键（`WHERE id = ?`），持锁临界区极小（仅 3~8ms），单行排队互不影响全馆其他数十万册图书的并发借阅。在单体多线程架构下，数据库行级悲观锁是以最低系统复杂度换取 100% 不可逆数据一致性的最优工程实践。”

### 深度追问 2：你提到把大模型调用从事务中剥离，具体是怎么落地的？如果剥离了事务，落盘失败了怎么处理？
- **面试官意图**：考察 Spring `@Transactional` 底层原理、事务传播机制（`Propagation`）以及与第三方外部 I/O 结合时的架构设计能力。
- **满分回答**：
  > “在最初代码中，AI 导读接口打了一个大的 `@Transactional`。因为调用远程 DeepSeek API 平均需要 2.5 秒网络 I/O，期间数据库连接被当前线程一直霸占，高并发下数秒就会耗尽 HikariCP 连接池。
  > **我们的具体解耦落地**：
  > 1. **方法物理拆分**：外层主入口方法不加任何 `@Transactional` 注解。先以只读方式查询本地图书基本信息，随后进行纯粹的异步 HTTP 网络请求；
  > 2. **独立新事务落盘**：为了防止 Spring AOP 自调用导致事务失效，我们专门抽取了独立的 Spring Bean：`AiInsightTransactionHelper`。外部 API 成功返回文本后，调用其被标注为 `@Transactional(propagation = Propagation.REQUIRES_NEW)` 的 `saveInsight` 方法；
  > 3. **落盘失败补偿与兜底**：如果数据库在落盘瞬间发生异常，外层捕获后将结果暂时写入 Redis 内存缓存并打点告警，确保当前正在查看详情页的用户依然能看到导读内容，实现了弱依赖下的服务高可用。”

### 深度追问 3：借书和还书死锁的拓扑排序，能不能详细讲讲你们怎么发现和验证的？
- **面试官意图**：考察并发 Debug 能力、死锁必要条件的理论功底以及测试验证闭环。
- **满分回答**：
  > “我们在 Stage 6 进行架构走查时，分析了借书与还书的时序图：
  > - 借书事务：读者选定某本大类图书发起借阅，业务首先扣减 `Book` 的 `available_stock`，再随机选取一个物理副本 `BookCopy` 并更新为 `BORROWED`。锁顺序为：`Book -> BookCopy`；
  > - 还书事务：馆员拿着物理条码扫码还书，系统由 `copyId` 查出 `BookCopy` 并更新为 `AVAILABLE`，然后再级联更新父表 `Book` 的可用库存。锁顺序为：`BookCopy -> Book`。
  > 
  > 当两名用户一个在借、一个在还同一本书时，交叉执行便构成了‘占有且等待’与‘循环等待’。
  > **我们的解决方案**：
  > 重构还书逻辑，在还书接口刚进入时，先根据 `copyId` 查出关联的 `bookId`，在尚未对 `BookCopy` 做任何变更前，严格先行执行 `bookRepository.findByIdWithLock(bookId)`，再执行 `bookCopyRepository.findByIdWithLock(copyId)`。
  > **验证手段**：
  > 我们编写了专用的并发集成测试 `LockOrderingTest.java`，启动 50 个线程高频混杂交替发起针对同一本图书的借阅与归还，捕获底层异常。重构后，经过全链路加锁拓扑审计与 DAG 偏序约束，根除了借还与预约主干路径的循环等待死锁，该并发测试连续运行上千次无死锁，充分验证了拓扑无环理论的正确性。”

### 深度追问 4：为什么不直接做基于全校用户矩阵的协同过滤（UserCF / ItemCF）？
- **面试官意图**：考察推荐系统在垂直领域业务落地中的架构选型认知，区分“盲目堆算法术语”与“懂真实工程取舍”的工程师。
- **满分回答**：
  > “我们在立项评审时深入评估过协同过滤，最终决定采用**基于读者历史偏好与在架库存感知的多路加权启发式推荐算法**，原因有三点关键的工程与业务约束：
  > 1. **数据极度稀疏（Extreme Sparsity > 99.8%）**：高校图书馆的借阅频次与电商浏览点击有本质区别。一个大学生一学期借阅量平均只有 5~15 本，而馆藏图书往往有数万乃至数十万种，读者-图书交互矩阵的稀疏度超过 99.8%。直接计算 UserCF 或 ItemCF 余弦相似度会导致绝大部分用户之间交集为 0，陷入严重的算法失效；
  > 2. **全矩阵计算高延迟与马太效应**：协同过滤在全量矩阵上的相似度更新复杂度高达 $O(U \times I)$ 或 $O(I^2)$，不仅对高校轻量化单体/微服务的高并发与实时响应极不友好，而且容易导致热门经典书被无限放大、冷门专业学术书无人问津的严重马太效应；
  > 3. **强实体库存约束（可转化性第一）**：通用 CF 算法哪怕推算出 99% 匹配的书，若该书全校仅 2 本且全被借走，读者看到却借不到，转化率为 0。我们采用**‘内容偏好（40%）+ 行为轨迹（40%）+ 全馆热度（20%）+ 在架可借强激励（+15.0分）’**的多路加权启发式召回，配合 PostgreSQL 存储层初筛下推，在 **45ms 内兼顾了推荐丰富度、冷启动友好度与 85% 以上的高可借转化率**，这是完全立足于校园图书馆真实流通特性的务实工程解。”

### 深度追问 5：在预约履约借阅（fulfillReservation）时，为什么一定要先锁 Book 后锁 Reservation？
- **面试官意图**：考察高并发锁拓扑偏序关系的全局严谨性，是否真正理解分布式/并发系统中的死锁预防定理。
- **满分回答**：
  > “这是我们在 Stage 9-A 进行全链路并发锁拓扑深度审计时做出的关键加固：
  > 1. **锁拓扑 DAG 偏序全局一致性**：在有向无环图（DAG）锁拓扑中，死锁预防的充要条件是全系统所有事务对资源加锁的偏序关系完全一致。系统中已确立了 `Book` 为根父实体、`Reservation` 与 `BookCopy` 为子实体的拓扑次序：统一为 `Book -> Sub-Entity`；
  > 2. **破除归还唤醒与预约履约的死锁环路**：
  >    - 当馆员还书触发 `returnBook` 时，系统先锁定 `Book`，在后置逻辑中唤醒下一个排队的预约，加锁拓扑为：`Lock(Book) -> Lock(Reservation)`；
  >    - 如果在读者到馆取书履约借阅 `fulfillReservation` 时，先根据 `reservationId` 加锁 `Reservation`，再调用借阅方法加锁 `Book`，加锁拓扑就变成了：`Lock(Reservation) -> Lock(Book)`；
  >    - 这两个事务并发交叉执行时，便形成了经典的交叉循环等待（Circular Wait）死锁！
  > 3. **工程重构落地**：我们在 `fulfillReservation` 中，进入事务第一步先通过只读查询获取其关联的 `bookId`，显式调用 `bookRepository.findByIdForUpdate(bookId)` 率先锁住父级 `Book`，持有父锁后再锁定 `Reservation`。从而将全系统的加锁偏序严格固化为 `Book -> Reservation`，彻底斩断了与归还唤醒并发执行时的循环等待链。”
